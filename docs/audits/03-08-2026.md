## 1. Resumen ejecutivo

GradeVision es un sistema de **corrección automática de exámenes de opción múltiple (OMR)** a partir de fotos tomadas con celular. El motor de visión y calificación (`gradevision_core`) está **bien modularizado**, con mensajes de error accionables, templates configurables, exports útiles (CSV, PDF, hoja marcada) y una documentación de producto **por encima del promedio** para un proyecto personal sin fines de lucro.

**Veredicto para demo/prototipo de escritorio:** el pipeline CLI es creíble y presentable, siempre que se cuente con fotos de prueba y un entorno de dependencias bien armado.

**Veredicto respecto al MVP de negocio** (docente sin conocimientos técnicos, uso desde el navegador del celular, cuenta por usuario, aislamiento de datos): **aún no está alcanzado**. Falta backend HTTP, autenticación, persistencia, frontend móvil y despliegue (Fases 1–6 del roadmap). La carpeta `backend/` solo contiene `README.md` y `requirements.txt`.

**Frase recomendada de posicionamiento:**

> *Motor de corrección automática listo para demo en escritorio; siguiente paso: API + web móvil según el roadmap del MVP.*

Evitar presentarlo como “listo para que cualquier docente lo use solo desde el celular”, porque eso contradice el estado real del código.

## 4. Fortalezas

### 4.1 Producto y documentación

- Problema de negocio claro (OMR caro vs. foto con celular), usuarios y restricciones bien definidos (costo cero, sin equipo dedicado, privacidad / Ley 25.326).
- MVP con **exclusiones explícitas** (app nativa, OCR de nombres manuscritos como requisito, multi-institución, integraciones tipo Classroom).
- Roadmap con **criterios de aceptación verificables** por paso: facilita colaboración y PRs acotados.
- Criterios de éxito del MVP de negocio son realistas y medibles.

### 4.2 Arquitectura del core

Separación de responsabilidades razonable:

| Módulo | Rol |
|---|---|
| `scanner` | Localizar hoja y corregir perspectiva |
| `detection` | Burbujas y organización en grilla |
| `grading` | Respuesta marcada y nota |
| `export` | CSV, PDF, imagen marcada |
| `templates` | Config de examen y listas de alumnos |

- Diseño pensado para reutilizar el motor desde un backend sin reescribir la lógica de CV.
- `pyproject.toml` declara el paquete instalable (`pip install -e .`).
- Funciones de export y carga reciben rutas como parámetros (buena base para no acoplar al CWD del servidor).

### 4.3 Experiencia ante fallos (CLI)

Mensajes de error **específicos y accionables**: foto borrosa, mala iluminación, hoja sin margen, pliegues / contorno no rectangular, cantidad de burbujas distinta a la esperada. En una demo, cuando algo falla, se entiende qué hacer. Cumple en espíritu RNF-02 (trazabilidad).

### 4.4 Decisiones de visión por computadora

- Binarización con umbral **adaptativo** (mejor tolerancia a iluminación despareja).
- Detección de respuesta por **oscuridad relativa a la fila** (no umbral global ciego).
- Manejo explícito de pregunta en blanco (`None`) y múltiple marcada (`"multiple"`).
- Templates con validación de divisibilidad preguntas/bloques.

### 4.5 Entregables de demo

- CSV consolidado (UTF-8 con BOM, delimitador `;` orientado a Excel).
- PDF individual por alumno (ReportLab, filas coloreadas).
- Hoja marcada (verde correcto / rojo incorrecto / amarillo clave).
- Flujo de lote en `main.py`: un fallo no detiene el resto (RNF-01).

### 4.6 Tests de dominio

- Tests unitarios de `grader`, `scoring` y `template_loader` **sin depender de fotos reales**.
- `pytest.ini` con `pythonpath = .` para imports simples.
- Buena base de testabilidad (RNF-05), aunque la cobertura es acotada (ver §5).

### 4.7 Privacidad en el repositorio

- `.gitignore` excluye `resultados/`, `sample_data/exams/*`, venvs y artefactos del paquete.
- Alineado con RNF-03 (no versionar datos identificables de alumnos).

## 5. Hallazgos y riesgos

Los hallazgos se numeran para referencia en PRs o issues futuros. La severidad es orientativa.

### H1 — Desfase narrativa MVP web vs. artefacto actual  
**Severidad: alta (producto / comunicación)**  
La documentación de negocio y el roadmap hablan de uso desde el celular sin terminal; el código entregable es CLI + JSON + carpetas locales. Riesgo: demos o conversaciones con docentes generan expectativas que el software aún no cumple.

**Mitigación:** README con secciones “Estado actual (demo escritorio)” y “Roadmap MVP”; versionar el alcance en cada release.

### H2 — Backend vacío con dependencias ya listadas  
**Severidad: media (expectativa / confusión)**  
`backend/requirements.txt` incluye FastAPI, Uvicorn, etc., pero no hay `app/` ni endpoints. Un colaborador puede asumir que la Fase 1 está empezada.

**Mitigación:** dejar explícito en `backend/README.md` “esqueleto de deps — sin aplicación aún” o implementar el `GET /health` del Paso 1.2 en el siguiente PR acotado.

### H3 — Dependencias inconsistentes entre fuentes  
**Severidad: alta (reproducibilidad de demo)**  

| Fuente | Contenido aproximado |
|---|---|
| `requirements.txt` (raíz) | Solo `numpy`, `opencv-python` |
| `pyproject.toml` | + `reportlab`, `pytesseract` |
| `backend/requirements.txt` | Stack web completo + CV |

Una instalación limpia solo con el requirements de la raíz **no alcanza** para ejecutar `main.py` completo (PDF, etc.).

**Mitigación:** una sola fuente de verdad (p. ej. deps de runtime en `pyproject.toml` + extras `[dev]` / `[backend]`), o un `requirements.txt` generado/alineado.

### H4 — Demo no reproducible sin datos de ejemplo  
**Severidad: alta (demo)**  
No hay `sample_data/exams/` versionado (y está en `.gitignore`, lo cual es correcto para fotos reales de alumnos). Sin un **pack de demo** (fotos sintéticas o de hoja propia del autor, o generador de hojas), un tercero no puede correr el flujo E2E en minutos.

**Mitigación:** carpeta `sample_data/demo/` con 2–3 fotos “buenas”, 1 “mala” (para mostrar diagnóstico), licencia/origen claros, y sin datos de menores.

### H5 — Conteo estricto de burbujas  
**Severidad: alta (robustez en aula real)**  
Si se esperan N burbujas y se detectan N±1, falla todo el examen. En fotos reales (manchas, tildes, resolución distinta, bordes de texto) es un modo de fallo frecuente.

**Mitigación (ideas):** umbrales de área relativos al tamaño de la hoja enderezada; reintento con parámetros más permisivos; imagen de diagnóstico con contornos aceptados/rechazados; mensaje con N detectadas vs. esperadas (parcialmente ya existe el mensaje, falta resiliencia).

### H6 — Organización de grilla por sort puro  
**Severidad: alta (corrección silenciosa incorrecta)**  
`organizar_en_grilla` parte bloques por orden en X y filas por Y. Con perspectiva residual o desalineación, puede **intercambiar opciones o filas sin levantar error**. Es el tipo de bug más peligroso en OMR: el sistema “funciona” pero la nota es incorrecta.

**Mitigación:** tests sintéticos de grilla; validación de espaciado/regularidad; anclas o ROI por template; rechazar si la geometría no es coherente.

### H7 — Contorno de hoja = contorno de mayor área  
**Severidad: media**  
Si hay objetos grandes en la escena, puede tomarse el contorno equivocado. La diagnosis de esquinas mitiga parte del problema, pero no hay candidatos alternativos (2.º / 3.º contorno) ni chequeo de ratio tipo A4.

### H8 — Umbrales de área de burbuja en píxeles absolutos  
**Severidad: media**  
`area_min` / `area_max` fijos no escalan bien entre resoluciones de cámara distintas. Lo ideal es normalizar respecto al área de la hoja enderezada.

### H9 — Módulo OCR de nombres (`student_name.py`) vs. decisión de producto  
**Severidad: media (diseño / portabilidad)**  
Existe OCR con Tesseract y ruta hardcodeada de Windows (`C:\Program Files\Tesseract-OCR\tesseract.exe`). La documentación de negocio **excluye** lectura automática de nombres del MVP y el flujo real usa lista manual. El módulo no se usa en `main.py` y añade fricción (dependencia nativa + path no portable).

**Mitigación:** marcar como experimental, mover fuera del path crítico, o eliminar hasta que haya un diseño de producto que lo justifique; nunca hardcodear rutas de instalación.

### H10 — I/O interactivo y `print` dentro de `gradevision_core`  
**Severidad: media (Fase 0 / reutilización en backend)**  
El README del core indica que solo ciertos módulos de templates hacen `input()`. En la práctica también hay interacción en `template_loader.elegir_examen_interactivo()` y `print` de diagnóstico en `document.py` y `grid.py`. Eso contamina el paquete “puro” pensado para backend.

**Mitigación:** menús solo en scripts de raíz (`main.py`, `crear_examen.py`); logging configurable en lugar de `print`; API de librería sin side effects de consola.

### H11 — Cobertura de tests acotada  
**Severidad: media**  
~8 tests, centrados en grading y templates. Faltan tests de:

- `organizar_en_grilla` con centros sintéticos
- pipeline de perspectiva / esquinas con fixtures de imagen
- conteo de burbujas y edge cases (0, N±1)
- exports (smoke: genera archivo y columnas esperadas)

### H12 — Entorno de desarrollo no versionado de forma reproducible en la auditoría  
**Severidad: baja–media**  
En el entorno de revisión no había `venv` ni `pytest` instalado globalmente; no se ejecutó la suite. No es un defecto del código en sí, pero refuerza H3 y la necesidad de instrucciones de setup de un solo camino.

### H13 — Criterio de éxito del MVP de negocio aún no cumplible  
**Severidad: alta (producto, no bug)**  
“Un docente sin conocimientos técnicos puede… sin asistencia externa” requiere la web móvil (Fase 6). Hoy el uso implica terminal, venv y estructura de carpetas. Correcto para prototipo; no para el criterio de éxito del §7 de requisitos de negocio.

### H14 — Artefactos de salida con nombres de alumno  
**Severidad: baja en demo local; alta en MVP web**  
PDF e imágenes marcadas usan el nombre del alumno en el filename. En local es aceptable; en servidor hay que combinar con IDs opacos, retención de fotos (RNF-08) y control de acceso (RF-12/13).

## 6. Detalle técnico por módulo (notas)

### 6.1 `main.py` (orquestador)

- Flujo E2E claro: validar → enderezar → detectar → grilla → scoring → calificar → export.
- Buen manejo de lote y asignación de alumnos.
- Acoplado a rutas por defecto (`sample_data/exams/`) y a menús interactivos: adecuado como CLI de referencia, no como API.

### 6.2 Scanner

- Pipeline clásico Canny → contorno máximo → 4 esquinas → warp: simple y didáctico.
- Validaciones de nitidez (varianza del Laplaciano) e iluminación: umbrales fijos (`80`, `40–220`); conviene documentarlos y, a futuro, calibrarlos con un set de fotos reales.
- Diagnosis de fallas de esquinas: muy valiosa para el usuario final técnico.

### 6.3 Detection

- Morph close + filtros de área/aspecto: enfoque estándar.
- `diagnosticar()` en burbujas es un buen punto de partida para imágenes de debug (aún no integrado al flujo principal de error).
- Grilla: ver H6.

### 6.4 Grading

- `grader.calificar`: lógica simple y testeable; nota sobre 10 proporcional a aciertos.
- `scoring.detectar_respuesta`: criterio relativo bien motivado en comentarios.
- Tests cubren correcto / incorrecto / blanco / múltiple.

### 6.5 Export

- CSV consolidado con sección RESUMEN + DETALLE: práctico para docentes.
- PDF legible; overlay visual en la hoja enderezada ayuda a auditar la corrección a ojo.

### 6.6 Templates

- JSON mínimo (`nombre`, `total_preguntas`, `opciones_por_pregunta`, `bloques`).
- Emparejamiento template/clave por convención de nombre de archivo: simple y frágil si se renombran a mano; aceptable en prototipo.
- CRUD interactivo completo vía `crear_examen.py`.

## 7. Posibles mejoras por fase / tiempo / alcance

Las mejoras se agrupan para no mezclar “dejar la demo impecable mañana” con “construir el producto web”. Cada ítem puede mapearse a un PR pequeño.

**Objetivo:** demo confiable, repo claro, colaboración fácil.

| ID | Mejora | Por qué | Esfuerzo |

### Fuera de alcance recomendado (mantener exclusión)

Coherente con `docs/requisitos_negocio.md` y `docs/requisitos_tecnicos.md`:

- App nativa en tiendas
- OCR de nombres como requisito del MVP
- Multi-institución / cursos compartidos entre docentes
- Integraciones Classroom / LMS
- Colas distribuidas y Postgres de pago en el MVP
- Formatos de hoja completamente arbitrarios o mixto de opciones por pregunta

Priorizar simplicidad operativa: el proyecto no tiene financiamiento ni equipo de mantenimiento.

## 8. Priorización sugerida para PRs de colaboración

Orden práctico si el objetivo inmediato es **colaborar por PR sin bloquear el roadmap del autor**:

1. **Docs y claridad de estado** (esta auditoría, README de estado) — bajo riesgo.
2. **Unificación de dependencias + instrucciones de setup** — desbloquea a cualquier colaborador.
3. **Pack de demo + (opcional) imagen de debug de burbujas** — eleva la calidad de la demo.
4. **Higiene del core** (sin `input`/`print` en librería; OCR experimental) — prepara Fase 1.
5. **Tests de grilla y scoring edge cases** — red de seguridad.
6. **Fase 1 backend** (`/health`, `/procesar`) — primer valor de producto web.

Evitar en el mismo PR mezclar “refactor grande de CV” + “meter FastAPI” + “rediseñar exports”: PRs chicos mapeables a un paso del roadmap.

## 9. Conclusión

GradeVision tiene un **núcleo de corrección más maduro y mejor documentado** de lo habitual en un primer prototipo orientado a docentes. Las decisiones de producto (privacidad, costo cero, exclusiones de alcance, asignación manual de alumnos) son sólidas.

El principal riesgo no es “falta de ideas”, sino el **desfase entre el MVP web descrito y el CLI actual**, sumado a **reproducibilidad de la demo** (deps + datos) y a **modos de fallo del OMR** (conteo exacto, grilla por sort, umbrales absolutos) que en aula real pueden castigar la confianza del usuario.

Como prototipo de motor para demo controlada: **aprobado con observaciones**.  
Como MVP de negocio autocontenido para docentes: **no listo**; el camino está bien trazado en el roadmap y conviene ejecutarlo por fases con PRs pequeños.
